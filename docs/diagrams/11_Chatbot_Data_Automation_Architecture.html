What this automation does

The chatbot's knowledge comes from a PostgreSQL database that people can update at any time. This process keeps the chatbot in step with it automatically. Twice a day, at 07:00 and 19:00, a job pulls everything that changed through a secure Data API. It prepares the changed records, adds them to a new version of the search index, tests that version, and switches the chatbot over only if the tests pass. Urgent changes can be pushed straight away with Sync now or a webhook. No step needs a person, and a failed run never affects what users see.

Most of it already exists. The job queue, change detection, chunking, embedding, versioned indexes with a quality gate, cache refresh, notifications and dashboards are already in the chatbot. The pieces marked new are what we need to build: the Data API connector, validation and safety limits, the twice-daily schedule with a monthly full rebuild, the embedding-model check, the live-value lookup for prices and other changing numbers, and the sync watermark and run report.

Each step explained

1 · Trigger

A

Scheduled trigger new

What happens: A scheduler starts a sync every day at 07:00 and 19:00 (India time). Every Sunday it also compares all record ids to find rows deleted outright, and once a month it rebuilds the whole index from scratch (step 9). All times are settings. If the server was down at a scheduled time, the missed run starts as soon as it is back.

Why: Data in PostgreSQL can change at any time. Two fixed runs mean the chatbot is never more than about 12 hours behind. 07:00 is before office hours (yesterday evening's edits are live when users arrive). 19:00 picks up the working day's edits.

Built on: The chatbot already has a background scheduler (alerts, nightly evaluation). New: the two sync times, the weekly check, the monthly rebuild and the catch-up rule.

B

Manual "Sync now" already in the chatbot

What happens: An administrator presses "Sync now" in the admin console, or calls the admin API.

Why: For urgent corrections, such as a wrong price or a withdrawn product, that cannot wait for the next scheduled run.

Built on: Existing: the admin console already queues sync jobs. The database sync becomes one more job type.

C

Change webhook (optional) already in the chatbot

What happens: If the team that owns the database can send a notification after a change, it calls our webhook and a sync starts within a minute.

Why: Gives near-real-time updates without polling the database every few minutes. It is optional: the twice-daily schedule still catches everything if a webhook is missed.

Built on: Existing: the signed, replay-protected webhook endpoint (/api/v1/webhooks/content-updated).

1

Sync job (queue) already in the chatbot

What happens: Every trigger creates the same job in the jobs table. A background worker picks it up. Only one database sync runs at a time: a second trigger during a run is merged into it, not started twice. The job holds a lease, so if the server restarts mid-run, the job is picked up again. Failures are retried 3 times with increasing waits.

Why: One entry point means the schedule, the button and the webhook all behave identically and are all visible in the admin console with their status and result.

Built on: Existing: the ingestion job queue and worker (ingestion/jobs.py, ingestion/automation.py).

2 · Extract & prepare

2

PostgreSQL (source of truth) already in the chatbot

What happens: The client's database holds two kinds of data. Content (FAQs, help articles, product descriptions, documents) changes rarely and is synced into the index. Live values (prices, fees, stock, seats, dates) can change at any time and are never indexed: when a user asks for one, the chatbot reads it from the Data API at that moment (see "Content or live value?" below). Each content table needs an updated_at timestamp and an is_deleted flag (or a deleted_records table).

Why: A twice-daily index can be up to 12 hours old: fine for an article, wrong for a price. updated_at lets us fetch only what changed; is_deleted lets us remove deleted content.

Built on: Owned by the data team. The chatbot never connects to it directly: only the Data API does, with a read-only database user (ideally on a read replica).

3

Data API (pull) new

What happens: The sync job calls GET /kb-export/changes?updated_since=<watermark>&page=N over HTTPS with an API key or OAuth token. The watermark is the time of the last successful sync minus a 5-minute overlap (to catch transactions that were still being saved). Results come page by page, for example 500 rows each. Network errors and 429/5xx responses are retried with back-off.

Why: An API keeps database credentials and table structure away from the chatbot. Paging keeps memory small. The overlap guarantees nothing is missed, and step 5 removes any duplicates.

Built on: New: a connector (a new source type next to page, sitemap, Zendesk and FAQ). The API itself is a small read-only service in front of PostgreSQL: either the data team's or a tiny one we deploy.

4

Validate & stage new

What happens: Each row is checked: required fields present (id, title, body, updated_at), correct types, sensible length. Order matters: personal data (phone numbers, individuals' emails, ID numbers) is masked first, in memory, and only then is the response saved as a dated snapshot. An unmasked copy is never written to disk. Safety limits stop the run if something looks wrong, for example if more than 20% of all records would be deleted, or the API suddenly returns 0 rows.

Why: Bad or partial data must never reach users. A broken export that looks like "everything was deleted" should stop the run and alert, not empty the chatbot. Masking before saving means the 30-day snapshots never hold personal data; they still show exactly what arrived in any run.

Built on: New: schema check and safety limits. Existing: the sensitive-data redaction already used for chat messages.

5

Detect changes already in the chatbot

What happens: A content hash is computed for every record and compared with the hash stored at the last sync. Each record is sorted into new, changed, unchanged or deleted. Unchanged records are skipped.

Why: Typically only a small share of records changes per run, so the run takes minutes, not hours, and costs no extra embedding work for unchanged content.

Built on: Existing: hash-based change detection and the document registry (ingestion/registry.py).

6

Preprocess already in the chatbot

What happens: Each record becomes a clean document: title, body text and structured fields written as readable text, HTML removed, whitespace and duplicates cleaned. Metadata is attached: record id, product, source table, last-updated date and who may see it (access roles). Text is scanned for hidden instructions (prompt injection).

Why: The chatbot answers better from clean, well-labelled text. Access roles keep internal records away from public users. The injection scan stops a database field from smuggling instructions to the AI.

Built on: Existing: text cleaning, metadata and injection scan used for files and web pages today.

3 · Index & quality gate

7

Chunking already in the chatbot

What happens: Only new and changed documents are split into small sections. Each section keeps its document title and source, so answers can cite it.

Why: Small pieces let search find the exact paragraph that answers a question.

Built on: Existing: the same chunking used for all current documents, so database content behaves like everything else.

8

Embedding already in the chatbot

What happens: Each new chunk is turned into a vector (a list of numbers that captures its meaning) with the same embedding model the chatbot uses for questions. The model name and version are pinned to the index version. Before an incremental sync, the configured model is compared with the live version's model: if they differ, the sync does not patch the index but starts a full rebuild with the new model.

Why: Vectors from two different models cannot be compared. If the model changed mid-way and only new chunks used it, the index would silently mix two sets of numbers and answers would get worse with no error.

Built on: Existing: the embedding model runs on our server (no per-use cost) and every index version records its embedding model. New: the check that refuses an incremental patch when the model differs.

9

New index version already in the chatbot

What happens: A new version of the search index is built next to the live one: the live content, plus new and changed chunks, minus deleted records. Once a month (and whenever the embedding model changes) the version is built from scratch from all current records instead. Users keep using the live version during the whole run.

Why: Users never see a half-updated index, and a bad update can be undone instantly. The monthly rebuild stops months of small patches from leaving an untidy index (leftover fragments, uneven chunking); it goes through the same quality gate.

Built on: Existing: versioned indexes (INDEX_VERSIONING_ENABLED, backend/indexing/versions.py).

10

Quality gate already in the chatbot

What happens: Before switching, the new version is scored on the golden test questions (does the right source appear in the top 5?) and must pass four checks: (1) the index is not empty and at least 5 test questions were scored (EVAL_MIN_CASES); (2) the score is at least the floor of 0.85 (EVAL_MIN_SCORE); (3) it is no more than 0.02 below the live version (EVAL_TOLERANCE) - no big step down; (4) it is no more than 0.05 below the best score any version ever reached (EVAL_MAX_DRIFT) - no slow slide through many small steps. The gate fails closed: if the score cannot be computed, the version is rejected, never passed.

Why: A data change can accidentally break answers, for example a renamed product or a deleted FAQ. Check 3 catches a sudden drop; check 4 catches a series of small drops that each look harmless; failing closed means a broken evaluation can never wave a bad index through.

Built on: Existing: gate_decision() in backend/indexing/versions.py (up to EVAL_GATE_MAX_CASES test questions). It uses search only, no AI model calls, so it costs nothing.

11

Promote or keep already in the chatbot

What happens: Pass: the live pointer switches to the new version instantly, with no restart or downtime. Fail: the live version stays as it was, and the team is alerted with the reason. The last 5 versions are kept, so an admin can roll back with one click.

Why: Users only ever see data that passed the checks.

Built on: Existing: promote / rollback and KEEP_INDEX_VERSIONS=5.

4 · Publish & monitor

12

Refresh answers already in the chatbot

What happens: Cached answers for the affected product are cleared. Approved FAQ answers that cite a changed or deleted record are flagged for re-check.

Why: Without this, a cached answer could repeat old information for hours after the data changed.

Built on: Existing: freshness handling and cache invalidation (ingestion/freshness.py).

13

Chatbot answers already in the chatbot

What happens: The next question is answered from the new data, with links to the source. A question about a live value ("What is the verification fee?") is answered from the Data API at that moment, not from the index.

Why: That is the goal of the whole process: content within 12 hours, live values always current.

Built on: Existing: the chatbot always reads the live index version. New: a live-value lookup (a read-only Data API endpoint the chatbot calls for prices and other changing numbers).

14

Record the run new

What happens: After a successful run, the watermark moves to this run's start time. A run report is stored: rows read, added, changed, deleted, skipped, duration, quality-gate score and index version. Every run, including failed ones, goes into the audit log.

Why: The watermark makes the next run incremental. A failed run does not move it, so nothing is lost: the next run simply fetches the same changes again. Reports answer "when was this data last updated?".

Built on: New: a sync_state table (watermark per source) and the run report. Existing: the audit log.

15

Notify & monitor already in the chatbot

What happens: A short summary goes to Teams, Slack or email (for example "07:00 sync: 12 changed, 1 deleted, gate passed, 4 min"). Grafana shows run history, duration and record counts. Alerts fire when a run fails, when the gate blocks a version, or when no successful sync has happened in 24 hours.

Why: The team learns about problems before users do, and can show when the data was last refreshed.

Built on: Existing: ADMIN_NOTIFY_WEBHOOK_URL, alerting (ALERTS_ENABLED), Prometheus + Grafana. New: the "no sync in 24 h" alert rule.

Content or live value?

Decide this for every table and field before building, because it changes where the data flows.

Kind of dataExamplesHow the chatbot gets itWhy
Content (paragraphs, explanations)FAQs, help articles, product descriptions, policies, how-to stepsSynced into the index twice a day (steps 1-15)Changes rarely; search by meaning needs it indexed
Live values (changing numbers and states)Prices, fees, discounts, stock or seats, dates and deadlines, order or certificate statusRead from the Data API when the user asks; never indexedAn index can be up to 12 hours old - a stale price is worse than no answer

Content that mentions a live value ("the fee is shown at checkout") keeps the wording but not the number. Personal records (one user's orders or certificates) are neither: they need the user to be logged in and go through the existing account check.

Data API contract (proposed)

A small, read-only API in front of PostgreSQL. It can be built by the data team, or by us as a tiny service using a read-only database user on a read replica or a database view.

Request

GET /api/v1/kb-export/changes
    ?updated_since=2026-11-24T01:25:00Z   (watermark minus 5 min)
    &page=1&page_size=500
Authorization: Bearer <token>

Weekly id check

GET /api/v1/kb-export/ids?entity=faq&page=1

Database needs: updated_at on every table used, kept current by the application or a trigger; is_deleted (soft delete) or a deletions table; an index on updated_at.

Security

AreaControl
Database accessThe chatbot never connects to PostgreSQL. Only the Data API does, with a read-only user, preferably on a read replica.
API accessHTTPS only. API key or OAuth client credentials kept in the secrets store (never in code or Git). IP allow-list where possible.
Personal dataThe export sends only fields the chatbot needs. Step 4 masks personal data as a second line of defence.
Who sees whatEach record carries access roles. Internal records are never shown to public users.
Malicious contentStep 6 scans for prompt injection. The webhook is signed and replay-protected.
TraceabilityEvery run, its counts and its outcome are in the audit log. Raw snapshots are kept for a set period (e.g. 30 days).
